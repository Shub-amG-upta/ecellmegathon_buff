# FieldMind — Boiler Operations Agent

Tick-based agentic system for a 67 TPH AFBC bi-drum boiler. Reads six sensor
tags plus engineer notes and structured records, maintains an internal picture
of the plant, and advises on what is happening and what to do.

Implements the plan of action document. Runs today on a laptop against the
Google API; the same pipeline runs offline on the Qualcomm QIDK (SM8650) via
LiteRT-LM by changing one line of config.

> **All data in this repository is synthetic**, generated by
> `data/generator/`. No figure here is measured plant data. The agent is
> advisory only — it never actuates anything.

## The model switch

This is the part you asked to be easy to change. **One line in
`configs/base.yaml`:**

```yaml
llm:
  backend: mock      # mock | gemini | litert
```

or at the command line:

```bash
python run_demo.py --all --backend gemini    # export GOOGLE_API_KEY first
python run_demo.py --all --backend litert    # QIDK attached over adb
```

| backend  | what it is | use it for |
|---|---|---|
| `mock`   | no network, no key, canned schema-valid replies | plumbing, CI, unit tests |
| `gemini` | Google AI Studio over plain HTTPS (stdlib `urllib`, no SDK) | developing agent quality before the board is ready |
| `litert` | `litert_lm_main` on the QIDK, over adb or on-device | the numbers that go in the writeup |

Everything downstream calls exactly one method:

```python
reply = backend.generate(prompt, role="diagnostician")
```

Same prompts, same JSON parsing, same repair retry, same action gate, same
metrics regardless of backend. Adding Qualcomm Genie or llama.cpp means writing
one class with one method and calling `register_backend`. Nothing else changes.

All three are in `fieldmind/runtime/llm_backend.py`, which is the only file in
the repo that knows how a model is actually invoked.

## Where things are

```
fieldmind/
  schemas.py              Fact, WorldModel, AgentEnvelope, Assessment
  runtime/llm_backend.py  <-- THE MODEL SWITCH (mock / gemini / litert)
  agent/
    l0_ingest.py          rolling 60-min window
    l1_checks.py          limit, rate, balance, validity, pattern -> Facts
    l1_symbolize.py       Facts -> evidence packet + signature
    l2_triage.py          decides whether the LLM runs at all (cost controller)
    l3_retrieve.py        signature match + note search, context budget
    l4_diagnose.py        Diagnostician (LLM #1)
    l5_verify.py          Verifier (LLM #2, adversarial, narrower view)
    l6_gate.py            citation check + action catalogue + escalation
    l7_memory.py          promotion gate for the experience store
    world_model.py        log-odds belief update, baseline freeze
    orchestrator.py       one tick, start to finish + degradation ladder
  kb/stores.py            asset model, case library, notes, experience
data/generator/           physics-lite simulator + episode builder
bench/                    harness (tick replay), evaluator (T1-T9), probe, tests
configs/base.yaml         every decision variable from §11.2, in one place
```

The agent core is **stdlib-only** on purpose so it can be copied to the device
without a scientific Python stack. PyYAML is the single dependency and is only
used to read the config.

## Current results — phase 2/3 baseline, `mock` backend, 30 episodes

**Read this table as "deterministic checks + signature retrieval, no language
model."** The mock backend just re-ranks retrieved cases; it does no reasoning.
These are the numbers the LLM has to beat, which is exactly what phase 2 of the
plan exists to establish.

| metric | value | target |
|---|---|---|
| Q1 state macro-F1 | 0.69 | ≥ 0.80 |
| Q2 top-1 RCA | 0.29 | ≥ 0.55 |
| Q2 top-3 RCA | 0.69 | ≥ 0.85 |
| Q3 evidence faithfulness | 1.00 | ≥ 0.95 |
| Q4 action recall / precision | 0.98 / 0.26 | ≥ 0.70 precision |
| Q5 false positives on normal | 5.7 /hour | ≤ 2 /hour |
| Q6 mean detection lead time | 15.4 min | report |
| S4 LLM invocation rate | 0.59 | minimise |
| S7 hard-stage deadline misses | 0.0 | must be 0 |

Faithfulness is 1.00 because the gate structurally cannot emit an uncited fact
id — it is a real property of the design, not a model achievement, and it will
only become an interesting number once a real LLM is generating the citations.

Action precision is low because the gate proposes every action attached to the
top two hypotheses; when the ranking is wrong the actions are too.

**Q5 is over target.** Threshold tuning against the normal episodes is
explicitly phase-2 work in the plan (§A.5: "these are starting values").
I have not tuned them, because tuning thresholds against the same 30 episodes
used to report Q5 would make the number meaningless.

Energy (S3) and therefore *energy per correct diagnosis* (S3/Q2) are **null**,
not estimated. They require the device.

## Four bugs worth knowing about, found while building this

These were caught by checking simulator output against the physics rather than
by trusting the code, and each one silently corrupted a whole fault family:

1. **Missing combustion controller.** Without a firing-rate loop tracking load,
   a normal load reduction left fuel unchanged and the bed ran away — every
   normal episode tripped. Not a fault; a missing controller.
2. **Leak had the wrong sign.** A tube leak was modelled as *reducing* heat
   absorption, which made the bed climb. Water sprayed into a furnace cools it.
   Family B looked identical to family D until this was fixed.
3. **No `SLOW` band in the symbolizer.** Case signatures use `SLOW`, the
   symbolizer only emitted `FLAT`/`MED`/`FAST`. Every `SLOW` triple in the case
   library was unmatchable, which silently zeroed families B and E.
4. **Drift check was not load-normalised.** Bed temperature tracks load, so a
   slow load swing looked exactly like fouling drift — 30 false positives per
   hour. Fixed by subtracting the load-explained component, using a coefficient
   (2.75 °C/TPH) fitted on the normal episodes only.

## Known gaps — do not report around these

- **Engineer notes are template-generated, not LLM-generated.** The plan calls
  for LLM generation in plant shorthand followed by hand-reading all ~150
  notes. `data/generator/notes_gen.py` uses templates as an honest placeholder.
  This is listed in the plan's own risk table at likelihood HIGH ("synthetic
  notes are too clean and make tier B trivial"). Replace before reporting any
  tier-B/C result.
- **Case library has 10 of 18 cases.** All five fault families are covered so
  the pipeline is exercisable, but retrieval coverage numbers off this seed set
  mean nothing. Open question 4 (how many cases to hold out) is still open.
- **T8 modality ablation runs but is not yet meaningful.** Notes only enter the
  pipeline through the prompt, and the mock backend does not read the prompt.
  T8 needs `--backend gemini` or `litert` to say anything.
- **T7 cross-episode memory is wired but unmeasured.** The promotion gate and
  experience store work; the paired empty-store/populated-store comparison is
  not automated yet.
- **`LiteRTBackend` flags are unverified against the board.** Run
  `python bench/probe_device.py` first. A wrong flag does not error — it
  silently falls back to CPU and produces a plausible, wrong number. The probe
  also checks that `libQnnHtpV75Skel.so` / `libQnnHtpV75Stub.so` are present,
  without which "NPU" numbers are actually CPU numbers.

## The two structural ideas

**The model never sees raw numbers and never has the last word.** L1 turns
numbers into Facts; L6 turns the model's answer into an approved Action. The
model works in the middle, where weighing several explanations against messy
evidence is genuinely useful, and where its tendency to invent things is boxed
in on both sides. Candidate causes come from an upstream walk of the plant
topology graph, so it cannot name a component that does not physically exist.

**Triage is the cost story.** Most ticks emit NORMAL without waking a model at
all. The LLM invocation rate (S4) is a headline result, not a footnote: it is
the difference between an agent that could run all shift on a battery and one
that could not. On the normal episodes it currently sits around 0.2.

The degradation ladder in `orchestrator.py` (rungs 0–5) is the mixed-criticality
contribution made concrete: HARD stages (L1 checks, L6 gate) always survive and
must never miss a deadline; SOFT stages (retrieval, both LLM calls) degrade by
*substitution* — smaller model, different backend, shorter context — rather
than by being dropped. At rung 5 with the LLM off entirely, the engineer still
gets "drum level falling 0.9 %/min, feed is 4.4 TPH short, water side." It just
stops explaining why. That safe floor is what makes the degradation story
defensible.

## Next steps, in order

1. `python bench/probe_device.py` on the QIDK — confirm flags and HTP libraries
   before anything else.
2. Run `--backend gemini` on all 30 episodes and compare against the baseline
   table above. **If the LLM does not beat it, that is a legitimate and
   reportable result** and the contribution pivots to *when* the LLM helps.
3. Replace template notes with LLM-generated ones; hand-read all 30 episodes.
4. Write the remaining 8 RCA cases; decide the hold-out with the advisor.
5. Lock the metric, clock and thermal protocol with the advisor **before** the
   sweep (§14.1 questions 1–4). Guessing wrong here means re-running the matrix.
6. Then `--backend litert`, backend sweep, Pareto plot.
